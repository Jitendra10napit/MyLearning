# 3. Architectural Styles Used

Instead of saying:

> "We use CQRS architecture."

Say:

> "Our application combines multiple architectural approaches. At the application level we use a layered/clean separation of concerns. For complex business operations we use CQRS. For asynchronous workflows we use event-driven architecture with Azure Service Bus. Azure Functions are used where serverless/event processing is appropriate."

This is a **much stronger Senior/Lead answer**.

CQRS itself should not be presented as the complete top-level architecture. Microsoft’s CQRS guidance explicitly makes this distinction: CQRS is intended to be applied where its benefits are useful, not necessarily as the architecture for the entire system. ([GitHub][3])

# 5. CQRS — Remember It Like This

Your Wiki should make CQRS extremely simple.

```text
                 CQRS

          ┌───────────────┐
          │ Application   │
          └───────┬───────┘
                  │
          ┌───────┴────────┐
          │                │
          ▼                ▼
       COMMAND           QUERY
          │                │
          ▼                ▼
       CHANGE            READ
        DATA             DATA
          │                │
          ▼                ▼
      Write Model       Read Model
```

### Command

> "Please change something."

Examples:

```text

UpdateCase
ApproveCase
CancelCase
```

### Query

> "Please give me something."

Examples:

```text
GetCase
GetCaseHistory
GetDocuments
SearchCases
```

### Most important interview point

> **CQRS does not require MediatR.**

MediatR is only one way to dispatch a command/query to its handler.

You can have:

```text
Controller
   ↓
Command
   ↓
Handler
```

without Mediator.

Or:

```text
Controller
   ↓
Mediator
   ↓
Handler
```

with Mediator.

This distinction should be prominent in your Wiki.

# 7. Why Azure Service Bus?

Don't memorize:

> "Service Bus is a messaging service."

Instead:

### Problem

If Case & Evidence directly calls every dependent service:

```text
Case & Evidence
   │
   ├── Workflow
   ├── Notification
   ├── Analytics
   └── Audit
```

you get tight coupling.

### Better

```text
Case & Evidence
       │
       ▼
Azure Service Bus
       │
       ├── Workflow
       ├── Notification
       ├── Analytics
       └── Audit
```

Now the producer doesn't need to know who consumes the event.

### Benefits

* Loose coupling
* Asynchronous processing
* Independent scaling
* Failure isolation
* Retry
* Dead-letter handling
* Multiple consumers

# 14. Important Corrections to Your Existing Design Pattern Page

There are a few places where I would make the explanations more precise.

### Singleton

Your Wiki currently maps configuration, cache, logging etc. to Singleton. ([GitHub][5])

For interview purposes say:

> "Singleton means one instance within the defined scope."

And distinguish it from:

```csharp
services.AddSingleton<T>();
```

`AddSingleton` is **ASP.NET Core's DI lifetime**, which provides one instance per DI container lifetime. It isn't automatically proof that you intentionally implemented the GoF Singleton pattern.

This distinction is excellent for a Senior interview.

---

### Observer

Your Wiki uses:

```text
Order Placed
    ↓
Email
Inventory
Billing
Analytics
```

That's a good conceptual analogy, but in enterprise architecture I'd explain:

> "This resembles the Observer pattern conceptually, while distributed systems commonly implement this using publish/subscribe messaging."

Then:

```text
GoF Observer
      ↓
Objects in same process

Pub/Sub
      ↓
Distributed components/services
```

That distinction shows architectural maturity.

---

### Middleware

Your Wiki maps ASP.NET Core Middleware to Chain of Responsibility. That's a good conceptual mapping. ([GitHub][5])

But say:

> "ASP.NET Core middleware pipeline is an example that strongly resembles Chain of Responsibility."

Avoid saying every middleware implementation is literally a textbook GoF implementation.

# 18. Your Interview Question Pages Should Change

Your current Senior Developer page has a good topic inventory covering OOP, SOLID, microservices, communication, Saga, Circuit Breaker, etc. ([GitHub][7])

But instead of:

> "What is Circuit Breaker?"

use:

### Question

**What is Circuit Breaker and where would you use it?**

### 30-second answer

> "Circuit Breaker protects our system from continuously calling an unhealthy dependency. Initially the circuit is closed. After repeated failures it opens and calls fail fast. After a recovery period it moves to half-open and allows limited requests. If the dependency is healthy it closes again. I would normally combine it with timeout, retry and proper fallback handling."

### Follow-up

**Retry vs Circuit Breaker?**

> Retry says **try again**.

> Circuit Breaker says **stop trying temporarily**.

### Project example

```text
API
 ↓
External Service
 ↓ failure
Retry
 ↓ failure
Circuit opens
 ↓
Fail fast
```

That is how your entire interview Wiki should be written.
